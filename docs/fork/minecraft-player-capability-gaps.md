# Minecraft 玩家能力缺口与实现路径

日期：2026-09-13。状态：能力盘点与实现建议，尚未作为新批次实施。

本文汇总普通生存玩家需要、当前 Fabric 主线仍欠缺的能力。弓、弩、三叉戟单独展开。本文也记录可继续复用的项目基础。

## 范围与判断方式

- 依据当前磁盘代码，包括 AIRI 与 `D:\mcpfabric` 的未提交修改。
- 以 Java Edition 1.21.1 为首个实现和验收基线。其他版本需要在模组侧单独验证。
- 能力判断以正式 `game-host` 领域工具、技能桥和客户端反射为边界。
- 调试探针或单独配置的原始 MCP 工具，不自动等于已接入领域执行契约的能力。
- 既有真机记录只证明记录中的场景。本轮未重新运行游戏验收。
- 下文的流程、字段与拆分都是建议。本文不新增运行时工具，不确定新依赖，也不重新批准既有批次。

“接口缺失”表示模组或领域层缺少必要操作。“接入缺失”表示已有部分原语，但正常工具或组合动作无法使用。“覆盖有限”表示已有实现，仍有明确的场景限制。

当前正式工具是 `game_observe`、`game_move_to`、`game_status`、`game_cancel`、`game_say`、`game_collect`、`game_follow`、`game_craft`、`game_drop`、`game_locate`。[领域工具清单][domain-tools]和[技能桥][game-bridge]共用领域执行路径。

## 1. 总体判断

当前主线具备有界移动、少量采集、简单合成、聊天和若干保命动作。它尚未覆盖普通玩家从开荒、补给到死亡恢复的完整过程。

最早阻断开荒的是工作台。`game_craft` 只支持玩家背包的 2×2 格子。超过尺寸的配方返回 `recipe_needs_crafting_table`。其他配方类型返回 `unsupported_recipe_type`。[合成实现][fabric-craft]

这意味着她能合成工作台这个物品，却不能把它作为 3×3 工作站使用。镐子、箱子、熔炉和床的正常制作流程会在这里受阻。

远程武器暴露的是另一组缺口：持续使用物品、瞄准、弹药状态、投射物归属和动作取消。补齐这些能力，还能支持钓鱼、盾牌、药水和部分移动技巧。

## 3. 远程武器：弓、弩与三叉戟

### 3.1 当前原语为什么还不够

`interact.attackEntity` 调用的是近战攻击。`interact.useItem` 可以启动主手物品使用，但没有武器任务状态。

`control.startUsing` 只设置使用键按下。`control.stopUsing` 清键并调用玩家的 `stopUsingItem()`。这条路径没有显式调用交互管理器的正常释放操作。[当前控制代码][fabric-control]

既有进食验收已经发现：只设置按键状态不足以启动一次物品使用。远程武器也需要分别验证开始、持续、正常释放和中止。不能把“按键已清除”当成“武器已发射”。[进食问题记录][reflex-evidence]

物品快照目前包含 ID、数量、名称和耐久。它没有输出弩内已装弹药、武器附魔、当前使用手和蓄力进度。实体读取也没有形成射手、投射物、命中目标之间的完整事件链。[玩家状态实现][fabric-player]

### 3.2 三种武器需要不同状态流程

| 武器 | 建议状态流程 | 需要读取的状态 | 必须处理的分支 |
| --- | --- | --- | --- |
| 弓 | 准备装备与箭 → 选择射击位置 → 蓄力并瞄准 → 正常释放 → 观察飞行和命中 | 武器、弹药、使用手、使用 tick 数、目标位置与速度、视线 | 蓄力不足、目标遮挡、无弹药、耐久不足、目标消失、蓄力中取消 |
| 弩 | 读取已装填状态 → 必要时装填 → 已装填待命 → 瞄准 → 再次使用发射 → 观察结果 | 已装填标志、装入的投射物类型、装填进度、影响装填或射击的附魔 | 空弩与已装填弩不能走同一开始逻辑，切换物品后保留装填，装填中与待命中分别取消 |
| 三叉戟投掷 | 准备装备 → 蓄力与瞄准 → 投掷 → 跟踪投射物 → 等待回返或规划拾回 | 当前三叉戟、附魔、耐久、投射物 UUID、拥有者、飞行或落地状态 | 无忠诚时遗落，有忠诚时等待回返，回收超时，背包空间不足，目标已经死亡 |
| 激流三叉戟 | 判断使用条件 → 检查推进路线 → 蓄力 → 推进 → 恢复稳定移动 | 游戏侧允许激流的条件、碰撞空间、玩家运动状态 | 激流属于玩家移动，不能套用投射物射击回执。条件不满足时明确失败 |

原版弓在释放使用键时射出，蓄力影响射击，箭有下坠。弩把装填和发射分成两个操作，已装填状态可以保留。[官方弓说明][bow-official]、[官方弩说明][crossbow-official]

普通三叉戟可以投掷后拾回，忠诚改变回收方式，激流改变玩家移动。引雷还受天气和命中条件影响。实现时由目标游戏版本判断这些条件，不把它们写成模型提示中的固定推断。[官方三叉戟说明][trident-official]

版本接口参考：[BowItem][bow-api]、[CrossbowItem][crossbow-api]、[TridentItem][trident-api]与[客户端交互管理器][interaction-api]。这些链接使用 Yarn 命名。本地 fork 使用 Mojang 命名，不能直接复制类名与方法名。

### 3.3 共用基础与武器差异

建议由一个武器执行模块负责装备、目标、输入所有权、使用状态和停止。弓、弩、三叉戟分别保留自己的状态转换。只有出现真实复用需求时，才继续拆分模块。

| 共用能力 | 建议责任 | 武器差异 |
| --- | --- | --- |
| 物品选择 | 从主背包、快捷栏或副手取得指定物品，读取最终槽位 | 三叉戟投出后离手，弩的已装填状态属于物品本身 |
| 使用状态 | 开始一次原版使用，按 tick 持续，区分正常释放与中止 | 弓和普通三叉戟在释放阶段产生投射物，弩需要另一次使用 |
| 弹药管理 | 读取可用弹药与实际消耗，处理缺货 | 无限附魔不能用“箭必须减少一支”判断发射，多重射击不能按单箭数量判断 |
| 目标选择 | 将用户目标解析为本次动作固定的实体 UUID | 目标消失后结束或重新规划，不能静默换成同类另一只生物 |
| 瞄准 | 读取眼位、目标碰撞箱、速度与遮挡，计算候选方向 | 弓蓄力与弹道相关，弩和三叉戟使用不同的游戏参数 |
| 发射前判断 | 每次发射前刷新目标、距离、视线和友方位置 | 穿透、多重射击、烟花和范围效果需要不同的命中区域判断 |
| 结果观察 | 跟踪本次动作的投射物和命中事件 | 三叉戟还需要独立的回收结果，激流读取玩家移动结果 |

瞄准先覆盖静止、无遮挡、短距离目标，再覆盖移动目标与高差。根据目标版本的速度、阻力和重力做有界轨迹预测。不要直接用“朝实体中心看”代替弹道计算，也不要依赖普通真实世界抛物线覆盖全部游戏物理。

水中射击、特殊弹药和内容模组武器单独扩展。首批可以明确只支持普通箭和普通投掷三叉戟。未支持的附魔或弹药组合必须返回能力限制，不能静默改成另一种操作。

### 3.4 控制频率与所有权

模型负责目标与策略，例如“用弓攻击这只僵尸，最多射三次”。主进程负责命令身份、租约、取消、工具登记和回执核对。客户端模组负责逐 tick 蓄力、瞄准与发射。

现有徒步和载具执行器分别以约 150ms、250ms 的间隔轮询，还要经过 MCP 与 HTTP。这个频率不适合直接承担发射窗口或落地水时机。实时逻辑应进入客户端的确定性执行流程。[徒步执行器][terrain-executor]、[载具执行器][vehicle]

射击期间，视角、手持物、使用键与移动输入必须有一个明确所有者。反射进食会换手持物，防御和脱险会改移动与视角。抢占时必须先终止武器状态，再允许下一位所有者接管。

当前命令注册表具备单写者与取消机制，但新地形执行器没有完整下传用于反射关联的命令身份。远程武器接入前，需要把命令身份与停止原因真正带到客户端动作中。[命令注册表][registry]、[地形接入位置][domain-tools]

### 3.5 取消不能简单地等同于松开右键

对弓和普通投掷三叉戟，正常释放本身可能就是发射。取消路径不能直接复用发射路径。

客户端需要区分蓄力中止与正常释放。中止方式必须用原版物品切换和使用协议做真机验证。如果某个状态下无法保证不发射，回执必须保留实际结果和不确定性。

| 收到取消时的状态 | 建议结果 |
| --- | --- |
| 尚未开始使用 | 不再装备或发射，释放本动作取得的输入所有权 |
| 弓或三叉戟正在蓄力 | 进入经验证的不发射中止流程，读取最终使用状态与物品状态 |
| 弩正在装填 | 中止继续装填，重新读取装填是否已经完成 |
| 弩已经装填 | 保留实际装填状态，不发送发射操作 |
| 投射物已经发出 | 停止后续射击。已发出的投射物继续存在，命令不能声称撤回了它 |
| 三叉戟已经投出 | 报告投出与回收状态。后续主动拾回需要新动作，原版自动回返仍由游戏处理 |
| 断线、死亡或维度改变 | 清除本地控制，终止旧命令，保留已观察到的投射物事实 |

网络重试也不能重复发射。主进程和客户端需要对同一命令下的发射序号去重。复用当前 `commandId` 与连接代次，再增加本次动作内的序号，不按目标名称猜测是否重复。

### 3.6 射出、命中、击杀、回收分别核对

| 结果 | 可以采用的证据 | 不足以证明的信号 |
| --- | --- | --- |
| 已装填 | 读取弩物品中的装填状态和投射物内容 | 等待了固定时长 |
| 已射出 | 观察到属于本玩家、本次发射的投射物。再结合武器和使用状态 | 工具返回 `ok`、摆臂动画、单独的库存差 |
| 已命中 | 投射物与目标的碰撞或伤害事件，关联射手、目标和世界 | 目标在附近掉血，投射物离开视野 |
| 已击杀 | 可归因的死亡结果，保留目标 UUID | 目标消失，或另一位玩家补刀后的死亡 |
| 已回收三叉戟 | 关联投射物的回返或拾取结果，以及相应物品重新入包 | 等待几秒，或收到另一把同 ID 三叉戟 |

回执建议携带目标 UUID、发射序号、投射物 UUID、使用的武器与弹药、消耗和耐久变化，以及各阶段的结果。具体字段需在正式契约中定稿。

如果服务端桥可用，优先从服务端取得命中与伤害归属事件。如果只能观察客户端状态，就报告较弱证据。未观察到命中不能直接记成未命中，更不能记成击杀。

完成判定沿用 `checked`、终态和后置条件的分离。`checked` 表示回执经过核对，不表示命中或任务完成。库存差也不能替代命中证据。

### 3.7 建议的远程武器验收

以下是未来验收建议，本轮没有新增或执行这些测试。

| 场景 | 需要证明的行为 |
| --- | --- |
| 普通弓单发 | 主背包取弓与箭，开始使用，正常释放，只生成一次发射，回执区分射出与命中 |
| 无箭、低耐久、目标消失 | 明确失败，不空转，不改打附近另一只生物 |
| 遮挡与友方进入射线 | 发射前重读环境，等待或结束，不使用旧视线结果 |
| 弓蓄力中取消 | 清控完成，没有因取消额外发射 |
| 空弩装填与发射 | 装填完成后保持待命，独立发射命令才射出 |
| 已装填弩切换后使用 | 读取保留的装填状态，不重复装填或提前射出 |
| 弩各阶段取消 | 分别验证未装填、装填中、已装填和已发射状态 |
| 普通与忠诚三叉戟 | 分别验证落地拾回和自动回返，回收超时如实报告 |
| 激流条件不满足 | 不按普通投掷静默执行，不报告虚构投射物 |
| 引雷或特殊弹药 | 条件满足才声称对应效果，附魔变化不套用普通弹药结论 |
| 其他玩家同时攻击 | 命中和击杀不能借用其他玩家的伤害归属 |
| 重复请求与回执丢失 | 同一发射不重放，未知结果保持待核对 |
| 反射抢占、死亡、断线 | 输入所有权收敛，不在重连后恢复旧蓄力或旧射击 |
| 移动目标与高差 | 固定距离、速度和装备，报告重复试验的命中率和失败类型 |

命令契约、状态转换、事件归属和重复请求用适当的自动化测试。Java 使用行为、服务端同步和真实弹道在固定世界中验证。具体通过阈值需在各武器首批规范中确定。

## 4. 其他关键缺口的实现要点

### 4.1 背包、容器与加工共用一个可靠基础

现有背包换槽固定使用玩家 `inventoryMenu`。工作台、箱子和熔炉需要读取当前菜单的身份、类型、槽位与状态版本。槽位数字不能跨菜单直接复用。[背包实现][fabric-inventory]

建议先支持打开、读取、定量转移和关闭。每次操作核对菜单身份与实际槽位。界面被玩家关闭、目标方块被破坏、距离过远、背包满和鼠标携带物，都要形成可解释的结果。

3×3 合成复用现有配方与回执流程，但领取前要核对产物和本次配方。当前合成会优先领取已有结果槽，取消后还可能留有配方残留。这些残留不能自动归入下一次命令的成果。[合成代码][fabric-craft]、[合成验收中的遗留记录][craft-evidence]

熔炼需要把“已投料”“加工中”“已取货”分开。等待熔炉期间不必一直占用玩家输入。工作站任务保留世界、维度、坐标与本次投入记录，重新靠近后再读取结果。其他玩家移动材料时，不继续使用旧槽位假设。

### 4.2 采集、建造和移动共享实际能力

跟随、采集、回收投射物和普通赶路应复用地形导航。各操作仍保留自己的目标与结束条件。

采集先读取工具与采掘资格，再执行破坏。拾取需要关联本次破坏，不能仅用整个动作期间的背包增长。当前实现主要采用库存差，会受到别人丢物品或其他拾取的影响。[采集执行路径][domain-tools]

材料统计和实际取物必须一致。当前地形规划会计入主背包垫块，但放置时只选快捷栏。补统一取物后，移动、建造与补给都能复用它。[放置执行][terrain-executor]

复杂地形需要更准确的碰撞与流体数据。现有分类表按方块 ID 做有限推断，未知方块多按障碍处理。该策略有助于保守规划，但不足以覆盖藤蔓、特殊形状和模组地形。[方块分类][block-view]

### 4.3 落地水与飞行使用客户端实时控制

落地水需要读取垂直速度、落点、可交互面、物品与维度条件。客户端在有界窗口内选择动作，再核对放水与落地结果。收水属于后续动作，不能在危险尚未结束时提前触发。

当前 `detectHazard` 没有坠落分支。已有水面的落点规划、允许更大 `maxFall` 和主动落地水是不同能力。[反射实现][fabric-reflex]、[移动配置][movement-types]

鞘翅沿用 [MC-3c][mc3c] 的条件批方向，但需要补空中展开和真实飞行状态。装备、展开、推进、巡航、进近与着陆分别核对。烟花使用成功不能单独证明已经飞行。[官方鞘翅说明][elytra-official]

飞行中的停止需要定义可执行语义。停止新任务与停止推进可以立即生效，但惯性和下落仍存在。着陆或保命收尾必须在飞行契约中说明，不能把清空按键写成已经安全停住。

### 4.4 生活玩法与模组玩法建立在操作能力之上

农牧、交易、附魔和酿药可以复用取物、交互、菜单和结果核对。特殊工作站仍需保留自己的业务规则。

MC-2 的知识卡保留 `lead`、`candidate`、`verified` 和模组集版本。后续可增加“验证这条知识需要什么动作”的信息。缺少机器操作能力时，学习流程保留候选，不能只因读懂配方就记录为实测成功。[知识分级][knowledge]、[探索流程][explore]

旧 Mineflayer 的[熔炼][old-crafting]、[装备与箱子][old-inventory]、[睡觉][old-movement]可以提供行为和失败场景参考。移植时保留 Fabric 主线的命令身份与回执边界，不恢复另一套并行控制所有者。

## 5. 建议实施顺序与代码落点

| 阶段 | 交付重点 | 主要落点 | 可见验收结果 |
| --- | --- | --- | --- |
| 1. 观察与物品使用 | 完整观察、装备取物、物品状态、使用生命周期、客户端动作身份 | 模组的玩家、背包、控制处理器，AIRI `game-host` 与共享契约 | 能从主背包装备物品，读取真实状态，开始和中止使用 |
| 2. 基础生存生产 | 容器、工作台、熔炉、工具选择、定点放置 | 模组的菜单与合成边界，`game-host` 领域动作 | 从原木开始制作工具，烧出铁锭，存入箱子，再取出指定数量 |
| 3. 生存连续性 | 食物补给、睡眠、重生、跟随与采集共用地形导航、反射关联 | 客户端反射，AIRI 地形与任务执行 | 能跟随采集、补给、被打断后停止，死亡后重新规划 |
| 4. 基础远程战斗 | 弓、弩、普通与忠诚三叉戟，投射物与命中回执 | 客户端武器执行，必要的服务端事件，领域工具与技能桥 | 单发、装填、投掷、回收、取消、重试和归属场景通过 |
| 5. 快速保命与进阶移动 | 落地水、完整载具、鞘翅、激流、炽足兽与跨维度 | 客户端实时动作与移动模式，复用 `movement` 和 MC-3 计划 | 受控高台自救，受控航线起飞到着陆，载具可正常取得和起步 |
| 6. 生活与内容模组 | 农牧、交易、附魔、酿药、红石、机器与特殊界面 | 既有操作的组合技能，必要的工作站适配，MC-2 | 目标玩法从获取材料到产出核对的完整流程通过 |

阶段 4 的短距离武器操作可在阶段 1 后先做独立验证。把它作为野外战斗能力交付前，仍需补齐阶段 3 的控制抢占与生存连续性。

拆分围绕稳定责任：主进程管任务与回执，客户端管实时动作，服务端在可用时提供权威结果。共享类型放在现有中立契约边界，IPC 沿用 Eventa。组合技能调用领域动作，不直接接管按键。

本文未进行新库选型。实施前先搜索已有内部实现。若仍需引入新依赖，再按仓库规则调研候选，并由用户参与选择。既有 `movement`、命令注册表、MCP 连接与技能运行时优先复用。

## 6. 当前项目做得比较好的基础

### 6.1 游戏动作已经有独立的任务生命周期

[命令注册表][registry]拥有命令身份、参数摘要、连接代次、写动作互斥、租约和终态。相同请求可取得已有结果，参数冲突会被拒绝。

这能支持熔炼、射击和长程移动共用停止与重试规则。后续重点是把身份和状态完整落实到每一种客户端动作，尤其是目前覆盖较少的新移动模式。

### 6.2 完成结论已有实测依据

领域回执包含最终快照与后置条件。移动会重新读取位置，合成会读取库存变化。[证据来源][provenance]和[完成门][authority-gate]区分普通游戏报告与经过核对的结果。

这为远程武器区分装填、发射、命中和击杀提供了现成位置。当前观察半径和采集归属还需要收紧，因此不能把现有 `checked` 当成所有事实都已充分证明。

### 6.3 实时保命已有客户端执行位置

[反射控制器][fabric-reflex]已经在游戏 tick 内处理脱险、进食和自卫。[生命周期守卫][fabric-guard]在死亡、断线和心跳丢失时清理控制。

落地水、蓄力控制和飞行收尾可以沿用这一执行位置。当前反射行为还比较简单，多种动作之间的输入所有权仍需补齐。

### 6.4 领域工具与组合技能复用同一条执行路径

[技能桥][game-bridge]调用同一个 `GameCommandPort`。模型直接调用与技能调用都进入命令注册表。技能已有工具声明、内容审阅、变更阻断和撤销机制。[技能验收记录][skill-evidence]

这适合把稳定动作组合成“补给”“采矿回家”“远程狩猎”等技能。技能复用可以建立在已经验证的动作之上，无需再建游戏专属脚本执行器。

### 6.5 世界事实与知识来源已有边界

[记忆来源][memory-source]保留游戏世界、维度、观察时间和连接信息。MC-2 区分网页线索、解析候选和游戏实测，还记录模组集版本。

这些信息有助于区分“以前在这里见过箱子”和“箱子现在还在”。它也为模组升级后的知识失效提供依据。当前通用 `connection-scoped` 身份与实验入口覆盖范围仍需保留在结果中。

### 6.6 规划与游戏控制已有可替换边界

地形规划读取方块快照，执行器通过[移动端口][movement-port]控制游戏。MCP 细节由[端口适配][movement-host-port]集中处理。

这一边界让导航逻辑可以单独检查，也让真实交互映射有明确落点。接下来值得做的是让跟随、采集和回收都使用它，并提高快照精度。

### 6.7 真机证据保留了实际限制

现有记录保留了取消未命中、矿车依赖夹具初速度、马的夹具条件和合成残留。它们能指导后续验收，也能避免把一次演示当成完整能力。

这套记录方法值得继续使用。每项能力至少区分接口可调用、受控场景通过和真实生存可用。发布结论只能达到证据支持的层级。

## 7. 后续批次的共同验收要求

- 缺材料、无目标、背包满或条件不满足时，返回可解释结果。
- 取消、租约到期、死亡、断线和维度切换后，输入所有权有明确终态。
- 网络重试不重复投料、发射、交易或丢弃物品。
- 结果丢失时保留待核对状态，不推断成功，也不重放不可重复动作。
- 材料变化与目标效果分别核对，保留其他玩家造成变化的归属边界。
- 自动化测试覆盖稳定的公共行为。游戏协议、菜单同步和物理动作通过真机验证。
- 夹具搭建可以使用管理命令。验收动作本身走正常玩家操作，并记录所有外部助力。
- 跨版本结论按实际构建与场景分别记录，不能从单版本通过推断全版本兼容。

测试范围沿用仓库 [Vitest 规则](../../.agents/skills/enforce-rules-for-vitest/SKILL.md)。本文只给后续验收建议，未将这些场景标记为已通过。
