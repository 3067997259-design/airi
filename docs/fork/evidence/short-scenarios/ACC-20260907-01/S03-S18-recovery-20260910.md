## S17：旧事实失效后仍用有效事实 —— **FAIL（新缺陷）**

### 做了什么

1. 发送「请记住一条可更正的事实：ACC-20260910-S17 的测试植物叫「青竹」。」→ 抽取为待审片段 `d64fda03-eead-40de-9588-8d88fb9c1909`。
2. 批准该片段（`setReviewStatus(id,'approved')`，与队列里的「批准」是同一个 action）。
3. 用显式纠正 action `reviseFact`（与「记忆浏览器」的「修正」按钮同一个 action，`memory-browser.vue:115`）把它改成「ACC-20260910-S17 的测试植物当前有效名称是「赤松」；「青竹」的说法已作废。」，`relation: 'supersedes'` → 新片段 `ea59d32d-a50e-4774-90dd-ee47183d871d`。
4. 批准新片段。`listPending()` 由 49 变 48 且不含 S17 条目 → 纠正已生效；旧片段被判为失效。

### 结果

| 检查点 | 结果 |
| --- | --- |
| 旧事实不再被当成现状 | ✅ 旧片段（`d64fda03…`）不在 `listShareableFacts` 结果里 |
| 有效事实进入记忆候选 | ❌ **新片段（`ea59d32d…`）也不在**。`listShareableFacts(scope, 10)` 与 `(scope, 50)` 都只返回同样 4 条，S17 两个 ID 都不出现 |

### 根因（代码定位）

`listShareableFacts` 要求候选带来源：`!!fragment.sourceContext?.sourceType && !!(sourceContext.sourceEventId || messageId)`（`packages/stage-ui/src/stores/modules/memory.ts:794`），`projectMemoryCandidate` 同样要求（`life-mode.ts:249-257`）。

而 `reviseFact` 调 `persistExtractions(memoryRepository, [revision], undefined, revisionScope)`，**第三个参数 `sourceContext` 传的是 `undefined`**，而 `persistExtractions` 只在有值时写 `sourceContext`：

```ts
// memory.ts:1256-1262
const persistedSourceContext = sourceContext ?? extraction.sourceContext
fragments.push(await memoryRepository.insert({
  ...extraction,
  ...(persistedSourceContext ? { sourceContext: persistedSourceContext } : {}),
  ...
}))
```

纠正记录本身也没有 `sourceContext` 字段（`memory.ts:904-916` 的输入里没有）。所以**通过纠正链路产生的有效事实永远拿不到 `sourceContext`，永远进不了记忆候选**。

### 影响

- 「不把旧名字当现状」这一半是对的（`factStatus` 过滤生效）。
- 但另一半「记忆候选和发言均使用有效事实」在纠正场景下**结构性不可达**：纠正后既没有旧的、也没有新的候选，社交考量只看得到别的东西。
- 建议修法（供修复方判断）：把被替换事实的 `sourceContext` 继承给修订片段，或在 `reviseFact` 的入参里带上当前消息来源；另需一个回归断言「批准纠正后，有效片段出现在 `listShareableFacts`，被替换片段不出现」。

### 残余风险（记录，不判失败）

`projectEventCandidate` 给 `tool/result`、`plan/update`、`task/update` 的 `occurredAt` 一律填 `0`（`life-mode.ts:186/196/220`），于是这些**完成类**候选永远不会进入 `expiredRefs`；它们只受 watermark（`consideredThroughSeq`）与 `consumedRefs` 约束。给模型的刺激文本也不含时间戳（`formatConsiderationStimulus`，`life-mode.ts:383-396`）。本次模型恰好沉默，但产品是**依赖模型不误判新鲜度**，而不是结构上排除。若要收紧，可给活动类候选补上真实 `occurredAt`，或让未消费的陈旧活动也走 `stale-stimulus`。

## S08：focused 门 —— BLOCKED（与上次同因，已复核）

- `resolveAttentionMode(tasks, focusedModeEnabled)` 要求 `focusedModeEnabled === true` **且**存在 `status === 'active'` 的任务（`packages/core-agent/src/attention/mode.ts:7`）。
- 本次运行端实测：`attention-tasks` 的 `tasks=0`、`activeTasks=0`、`eventLog=0`；`attention.focusedModeEnabled=false`（本 profile 的本地设置即为关闭，需在「设置 → 机体模块 → 注意力」打开）。
- 任务只能由 server channel 的插件协议事件投影出来：`task:start` / `task:progress` / `task:blocked` / `task:done`（`packages/stage-ui/src/stores/tasks.ts:45-125`，经 `stores/mods/api/channel-server.ts` 与 `context-bridge.ts` 接入）。仓库内**没有任何插件或服务发布这些事件**（全仓仅 `plugin-protocol` 定义、`memory-core` 测试与 stage-ui 投影方引用），已确认没有 UI 路径可以产生 active 任务。
- 结论：与 [S07-S20-social-stimuli.md](./S07-S20-social-stimuli.md) 的 S08 结论一致，仍为 BLOCKED。要关闭它需要真实的外部插件（例如 Minecraft 集成那类）发布 `task:start`；用独立客户端连 server channel 直接发协议事件属于「制造协议事件」，本次未做。

## S09：speech-active 门 —— BLOCKED（阻塞条件仍存在）

- 当前配置：`speech.activeSpeechProvider = official-provider-speech`，`activeSpeechModel=auto`，`activeSpeechVoiceId=jilingshaonv`，`configured=true`，但 `speechProviderError = audio voices upstream 401: {"error":"UNAUTHORIZED","message":"Unauthorized"}`。

- 结论：维持 BLOCKED。阻塞点是**语音 provider 上游 401**，不是模型额度；需要可用语音来源后才能重跑。
