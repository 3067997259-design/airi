## 1. #18 恢复副本 journal：replay 与落盘（**发现新缺陷并已修复**）

### 1a. 复现（修复前，同一副本同一构建）

新构建首次启动后，`runtime-journal` 状态：

```json
{"currentSessionId":"2l-pZQRE4Fwfz1N_Gt2XV","len":4839,
 "first":{"seq":0,"createdAt":1788952312117},"last":4838,
 "status":{"pendingCount":1,
   "lastError":"journal sequence conflict at seq 0: the renderer appended without replaying the persisted session",
   "lastSeq":4838,"complete":false}}
```

- replay **已经生效**：内存 4,839 条、seq 0..4838、header `createdAt` 与磁盘一致（`1788952312117`）。
- 但队列里仍压着 1 条永远写不进去的行，且错误是 `seq 0` 冲突 ⇒ 该会话的整条队列被顶住，
  后续事件只留在内存里（`complete: false`）。这正是 #18 想消除的失败模式，只是触发路径不同。

### 1b. 根因（读代码 + 状态验证）

`packages/stage-ui/src/stores/journal.ts` 的 `hydrate()` 第一行是 `ensureSession(sessionId)`。
`ensureSession` 为新会话建 store 时会**立刻**把一个自造 `session/header`（seq 0，`createdAt = Date.now()`）
排进持久化队列。恢复副本的同一会话文件里 seq 0 是**另一份** header，宿主按
`seq + 内容指纹` 去重（`journal-host/index.ts:184-193`），于是：

1. 启动时某条路径（`ensureSession`/`append`/`readSession`）先为活动会话建 store → 自造 header 入队；
2. flush → 宿主发现同 seq 不同内容 → 抛 `sequence conflict at seq 0`；
3. 随后 `hydrate` 读文件、用文件内容重建 store —— 但**队列里那条自造 header 仍在**，
   每次重试都再次被拒，整个会话的队列从此不动。

离线回归没抓到它，是因为那些用例的假 port 不去重（`append` 一律接受），没有模拟宿主的冲突规则。

### 1c. 修复

- `hydrate` 不再先建 store：先 `await persistencePort.read(sessionId)`；
  - 文件为空 → 才 `ensureSession`（此时自造 header 归本进程所有，应当落盘）；
  - 读等待期间若已有 live 事件（`hasLiveEvents`，>1 条）→ 保持既有 live 历史，不覆盖；
  - 文件有内容 → 用文件内容 seed，并 `dropQueuedHeader(sessionId)` 丢掉此前排队的自造 header
    （那条 header 已不可能被接受；此时队列里也只可能是 header），队列清空则同时清掉
    `lastPersistError`，不再报告已经消失的“顶住”状态。
- 回归：`packages/stage-ui/src/stores/journal.test.ts`
  「does not wedge a replayed session behind a header queued before the read」——
  假 port 按宿主规则做 `seq → 指纹` 去重，同 seq 不同内容抛错。
  修复前该用例失败（`pendingCount: 2`），修复后通过。
