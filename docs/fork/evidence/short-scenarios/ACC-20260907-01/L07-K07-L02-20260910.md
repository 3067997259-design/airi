| 产品侧的根切换提示是否存在 | ✅ 注入过 `Workspace root switched to …; Paths in earlier turns refer to the previous root.` |
| 长期目标的环境变化门 | ❌ **没被触发到**：该目标从未拿到 Flow 槽（`longGoal.waitReason = "Waiting for another goal that holds the single Flow slot."`），`lastEnvironment` 始终为空，因此没有可比对的环境 |

### 由此得到的三条观察

1. **模型可以自己把工作区根改回去**。`setWorkspaceRoot` 在工具面里，而提示词只说「早前轮次的路径属于上一个根」，
   没有说「根是用户设定的，不要自行改回」。第二个模型把用户刻意的切换当成事故还原了——对用户来说这是
   「助手悄悄撤销了我的配置」。
2. **从未启动过的长期目标没有环境基线**。`checkStartConditions` 只在成功启动时记录 `lastEnvironment`；
   没跑过的目标在环境变化后首次启动时没有任何变化可比对（工作区根不匹配那道门仍然有效）。
3. **调用方传错 `characterId` 会造出永远起不来的目标**。`createSession(characterId, options?)` 的第一个参数是
   characterId；本轮我先误传了 `{}`，于是会话 meta 记成 `characterId: {}`，用它建出的长期目标
   `scope.characterId = {}`，此后每次唤醒都被第一道门拒绝，理由却是
   `The current user or character is outside the goal scope.`——没有指出「计划作用域本身是坏的」。
   （诱因是调用方误用；产品侧值得加一条入参校验 + 更准确的拒绝理由。）

## 顺带发现：记忆库连接被卡死过一次（重启后恢复）

在删目标之前的一次 `plansStore.softDeletePlan()` 之后，**所有** DuckDB 查询都开始抛
`TypeError: Cannot read properties of undefined (reading 'peek')`，`memory.databaseStatus` 变成 `error`：

```
{status:"error", error:"Cannot read properties of undefined (reading 'peek')",
 pendingErr:"TypeError: … 'peek'", shareable:0, totalErr:"TypeError: … 'peek'"}
```

重启应用后完全恢复：`status: ready`、77 条片段、3 条 shareable。
之后用同一个 id 再调 `softDeletePlan` 成功且库保持 `ready`，**无法按需复现**。

判断：一次失败查询可能把 renderer 内的 DuckDB 连接卡死，此后所有记忆查询都失败到重启为止。
本轮无法确定诱因（候选：中途终止的导入、两次 embedding 迁移、`softDeletePlan` 本身）。
建议修复方补一条：DuckDB 查询抛错后不要让连接永久不可用（重建连接或至少给出可读状态）。

## L07 双窗口竞争 —— PASS

夹具：`workspace/L07d-20260910/brief.txt` = `L07D-TOKEN-C41B78`。

1. 主窗口用 `/flow` 起一条有界 Flow：第一步 `bash sleep 90`，然后读 brief 写入 `initial-result.txt` 并读回。
2. 在 `sleep 90` 挂起期间，从**两个窗口的主输入框**分别发送**同一条修订**
   「不要写 initial-result.txt；改写到 revised-result.txt 并读回核对」：

   | 发送方 | 时刻 |
   | --- | --- |
   | 设置窗口（follower） | 00:46:04.678 |
   | 主窗口（leader） | 00:46:05.103 |

   两条间隔 **0.43 秒**，都落在 Flow 的等待窗口内。

3. journal `abfa404f896ae07d3754dead4727c110.jsonl`：

```
seq=1  flow/start            sYW0Solw
seq=5  user/message          第一步必须用 bash 执行 sleep 90…
seq=28 user/steering         修订：不要写 initial-result.txt；…
seq=29 user/steering         修订：不要写 initial-result.txt；…     ← 两条都记录，未被吞
seq=30 flow/step continue
seq=51 flow/step continue
seq=72 flow/completion-review
seq=73 flow/end done
```

工作区最终只有 `brief.txt` 与 **`revised-result.txt`（00:47:17 写入）**，**没有** `initial-result.txt`。
模型收尾回答：「按你后续的转向要求，未写入 `initial-result.txt`，而是直接写入了
`workspace/L07d-20260910/revised-result.txt`；经 `read` 工具回读核验，内容完整一致」。

**结论**：两条来自不同窗口的竞争性转向都被记录、按同一条计划车道收敛、旧目标零写入、
新目标写入并读回、Flow 只结束一次（`done`，完成门有 `flow/completion-review`）。L07 的这个变体 PASS。

## K07 两窗口并发点击 —— 部分完成（两窗口机制已验，真正的竞态没造出来）

- **已验**：设置窗口（follower）里对 probation 条目点「批准」，决策经 leader 落地后
  两个窗口的 `skills-review` 状态一致（`queue` 由 `opencode-adapter:probation` 变为 `:reviewed`，
  `probationCount` 1 → 0，`reviewedSkills` 增加该条目）。跨窗口的 leader 路由与状态复制是好的。
- **没造出竞态**：要做到「同一时刻两个窗口点同一动作」，需要一个**可操作的**队列条目。本轮
  唯一进入 probation 的是内置骨架 `opencode-adapter`，它在准备阶段就被批准了；
  重新制造条目的两条公开路径都无效：
  - 「提交审阅」对**已审阅**的目录条目是**静默无效**（点了之后队列、按钮都没变化）；
  - 只有「查看源码与自测」之后「批准」才真正生效——**未读源码时点「批准」也是静默无效**。
  两条都已在待修清单登记（无反馈的静默空操作）。
- 因此并发口径留待修复方补上反馈后可重跑：建议两条一起修，之后「一个窗口批准 + 一个窗口拒绝」
  同一 probation 条目就是现成的竞态用例。
