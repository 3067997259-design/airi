# ab-23 飞控修复执行方案

日期：2026-09-21。状态：设计建议，尚未实现。

本文件承接 [ab-23 审计](./elytra-flight-control-ab23-audit-20260921.md)。编写时重新检查了审计保存的源码哈希：FlightSession、FlightController、FlightDynamics、FlightRecovery、E-02 夹具及 ab-23 原始日志均未变化。本次只新增本文件，没有修改运行代码、操作 bot 或提交。

目标是让“可行候选”“实际执行”“安全收尾”采用一致的状态和规则，再判断这条路线需要怎样的高度余量。当前不以修改 A*、抬整条路线、扩大到达半径或放宽水体碰撞作为修复入口。

## 1. 先固定判断依据

ab-23 的完整臂在首次失败时位于 y=73.36。它瞄准 y=66.5 的近处航点，生成的四个俯仰都是向下：18.35° 至 58.35°。预测游标会越过航点，但预测姿态仍保持不变，评分也仍使用旧目标。此前平水面反例已证明：这个候选集能够把存在平飞动作的状态判为无解。

因此，“水上路线太低”不是目前唯一、也不是完整臂最先暴露的原因。真实路线最低点 y=63.5 的确需要后续检查，但应先关闭控制器自行制造的持续俯冲。

恢复开始时的控制接续已经改善。恢复结束时仍直接放手，随后发生掉血。完整臂可见掉血 6.64007，分腿臂 0.685335。恢复阶段零点火只能说明当前规则没触发，不能证明无需点火。

本轮必须分别回答三个问题：

1. 从当前实测状态，是否存在通过完整碰撞检查的控制策略？
2. 控制器实际执行的动作，是否来自该策略及同一时刻的完整状态？
3. 路线失败后，是否仍有人控制飞机，直到确认结束、完成原子转交或明确耗尽授权期限？

## 3. 批次 A：先让证据和控制权可信

### A1. 夹具先处理终态

修改 `apps/stage-tamagotchi/src/main/services/airi/game-host/movement/e02-route.integration.test.ts`。

当前循环先判断下一腿，再判断 terminated/revoked。将顺序改为：

```text
读取本次 status
保存全部新增 native tick 样本
如果是首次路线失败：固定失败 tick、session、revision、原因
如果路线已结束：转入结束阶段观测，不再提交普通下一腿
否则：按协议允许的 running/holding 条件决定是否预交接
```

具体要求：

- 删除把 `state !== 'running'` 整体视为可交接的判定。accepted、terminated、revoked 各有不同含义。
- 第一次失败的标识一经记录，不因后续状态、revision 或会话变化而重设。
- 交接应使用本次读取的状态。提交后的新 receipt 不得与提交前的旧 status 拼成同一次状态转换。
- 收尾阶段继续保存同一套遥测。不要再维护删减字段的 post-end 样本对象。
- routeCrossing 与 recoveryCrossing 使用同一个几何截面检测器，再按当 tick 的所有者和飞行状态分类。
- 恢复越过 z=20 不计航路验收成功，但应保留为真实几何事件。

### A2. 路线结果与物理控制阶段分开

在 FlightController 内保留两类事实。字段名可随现有代码调整，含义不能混用：

```text
routeOutcome: running | completed | failed | revoked
flightPhase: prepare | track | hold | recover | land | settled | released
```

`routeOutcome=failed` 不代表 `flightPhase=released`。第一次 no_viable 应固定路线失败结果，同时进入 recover。后续成功落地也不能把路线失败改回成功。

每个 native tick 只允许一个分支产生并提交最终 InputFrame：

```text
处理显式撤销、死亡、断开、维度变化及硬期限
按当前 phase 处理一次状态转换
从当前 phase 计算一个 InputFrame
统一提交一次输入
统一记录该输入的所有者、动作和转换原因
```

关闭 `driveSession()` 后又 `driveRecovery()` 的顺序双写路径。不要仅给第二次写入加一个条件后保留两套所有权事实。

恢复期间收到普通 submit/handover，本批一律返回明确的 `recovering` 拒绝，保留当前恢复会话、冷却、窗口和失败原因。不要接受新会话后再依赖它失败来恢复。恢复转回新路线的原子转换可以后做，不作为本批必要功能。

如果后续实现恢复转回路线，必须先从同一个实测 tick 验证新路线接入，再原子替换所有者。保留控制租约、boost、冷却及资源状态；转换前不得写新输入，转换后不得再写旧恢复输入。

### A3. 同步主机与保护器

需要一起检查以下消费者：

| 位置 | 必须修正的含义 |
| --- | --- |
| `FlightController.hasLiveChannel()` | 业务会话结束不应让仍持有有效控制期限的恢复阶段失去输入保护 |
| `ClientControlGuard.java` | 用“当前合法持有自主输入”的事实判断心跳豁免，同时保留撤销及硬期限约束 |
| 主机 `flight/channel.ts` | poll 的路线 ended 与物理控制 released 分开；恢复期间不能启动另一个控制器 |
| 主机 `flight/channel.ts` 的 submit 重试 | `recovering` 不得走“撤销旧 session 后重试”分支 |
| 主机 `flight/channel.ts` 的 revoke | 显式取消仍须能撤销恢复；不能因业务 ended 就提前 return |
| 主机 `movement/elytra.ts` | 从通道切到主机 safety-landing 前，必须有确认的控制移交，不能只看 endReason |
| `movement/port.ts`、`movement/host-port.ts` 及对应桥接契约 | 传递 phase、实际 owner、路线结果和恢复原因，不以缺字段推断已释放 |

现有主机有落地和收尾能力，应复用其落点选择。不要并行运行客户端恢复和主机启发式收尾。主机异步查找落点期间，当前合法所有者继续执行已经验证的短段。

### A4. 修统计，不再从最终 HP 推测伤害

每 tick 一起重置 collision、floor、speed、terminal 拒绝计数，以及首拒信息。累计值需要独立命名，禁止复用每 tick 字段。

每个被拒候选只计一次首拒原因。输出 evaluated、feasible、rejected、未评估数量/预算耗尽标志。完整评估后，首拒计数之和应等于被拒候选数，而非超过候选总数。

分别记录：获选候选的预测末态/最低净空/策略，以及首个失败候选的拒绝信息。不要把后者展示成获选候选即将发生的碰撞。

按 native tick 去重、检查连续性。以首次路线失败为 ending 起点，保存：

```text
endingMinHealth = min(结束阶段全部已观测 HP)
endingHealthDropFromStart = max(0, 结束阶段起始 HP - endingMinHealth)
endingObservedDamage = sum(max(0, hp[t-1] - hp[t]))
```

同时记录 firstDamageTick、掉血事件及缺帧区间。`endingObservedDamage` 是采样可见伤害下界；同 tick 治疗可能抵消伤害。若要精确总伤害，再接原生伤害事件。

把结果拆为 `settledGround`、`settledWater`、`unresolvedAirborne` 与 `damageFreeObserved` 等独立事实。只有完整观测、满足稳定落地和无可见伤害，才允许产生无损落地通过结论。稳定入水应保持独立失败分类。

## 4. 批次 B：模拟控制策略，而非固定姿态

主要位置：`FlightSession.tick/evaluate/advanceEntries/verifyHold`。保留已经核对过的 FlightDynamics 单步顺序。

### B1. 明确被预测的对象

候选应表示一个小型反馈策略，例如“随路线更新方向、俯仰保持水平、此刻不点火”。它不是未来 20 tick 都不变的一对 yaw/pitch。

从不可变实测快照建立候选自己的模拟状态，至少包括：位置、速度、姿态、路线进度、飞行阶段、boost 剩余、点火冷却、可用烟花、终端策略。每个候选独立推进，不得改真实游标、真实库存或真实冷却。

推荐第一版流程：

```text
for 每个有界候选策略:
    sim = 完整复制当前实测状态
    for k in 0..预测时域-1:
        更新 sim 的路线进度
        按 sim 的当前进度选择局部参考
        按候选策略与当前参考计算本步输入
        next = FlightDynamics.step(sim, input)
        扫掠检查 sim -> next 的机体、介质与已知空间
        推进 boost、冷却、库存、阶段和路线进度
        sim = next
    从 sim 继续验证实际可执行的终端/继续策略
    按路线进度与跟踪质量评分
只执行获选策略的第一步
```

不要在预测内递归调用整套 tick 搜索。候选内部每步只调用有界的参考选择、反馈规则和一次物理推进。

实际下一 tick 会从新实测状态重新规划。因此不能要求“上一轮预测的第 2 步”等于“下一轮重新选出的第 1 步”。要求的是：给定相同状态、策略、地图和参考，预测与执行计算出的动作相同。策略变化必须可追溯。

把上一 tick 获选策略作为下一 tick 的优先基线之一，重新用当前状态检查。不要因预算顺序而遗漏已经存在的安全候选；也不要未经复检直接执行旧预测后缀。

### B2. 补动作覆盖，但控制候选总量

可以先用以下组合作为有界起点，不宣称这些角度是最终参数：

| 维度 | 第一版候选 |
| --- | --- |
| 横向偏置 | 现有 5 个 yaw 偏置，围绕每一步更新后的路线方向 |
| 俯仰策略 | 当前参考瞄准角；参考角减 12°；绝对 0°；绝对 −12° |
| 首步点火 | 不点火；满足库存、冷却、无活动 boost 时点火 |

上限为 5×4×2=40。正俯仰向下，负俯仰向上。相同角度应去重。保留合理角度和转向速率约束，预测与实际采用相同限制。

这里推荐替换有界候选组，而不是在原来 40 个后追加两类、再让预算截断永远吃掉最后的保命动作。预算调度应优先覆盖上一轮基线、水平与拉起等不同策略，再扩展侧向组合。

首批预测不依赖没有建模的未来点火。`fireNow` 只在第一步执行；若终端策略需要未来点火，必须显式推进冷却、库存和 boost，并在真实执行中采用同一策略。点火失败或库存变化必须触发重验。

没有任何角度天然安全。水平与拉起候选也必须通过水体、岸壁、低顶和机体扫掠。加上绝对 0°只是关闭动作覆盖缺口，不是对实机场景的安全保证。

### B3. 统一进度、参考与评分

真实推进和预测推进共用同一套航点到达/过站语义，保留末点不能被普通过站规则提前完成的约束。

用单调路线弧长或稳定全局索引记录进度。分腿的局部 cursor 不能直接拿来与完整臂比较。至少保存 routeId、revision、局部索引及其对应的全局进度。

选择参考点时只在当前连续路线邻域前进，不能取全路径最近点，以免 U 形河湾跳到另一侧。到达半径只用于路线推进，不是允许机体切弯的净空证明。

先保留当前航点参考，让“每步更新方向”独立生效。如果随后出现近点俯仰抖动，再加按速度计算的前视距离。前视点应沿已验证折线取样，所有实际运动仍要扫掠，不能把跨折线的直线当成已验证航段。

评分不再使用进入预测时的旧目标距离。建议明确顺序：

1. 先删除碰撞、入水、未知空间、不可执行终端或资源不合法的候选。
2. 求全部可行候选的最大路线进度；选择距最大进度 1 格以内的一组。
3. 在这一组内比较横向误差、局部高度偏差及控制变化；等价带须固定并记录。
4. 只有前述质量等价时，才优先少用烟花；最终用稳定策略 ID 打破平局。

不要用两两“相差 1 格算相等”比较器滚动选择。该关系可能不传递，导致候选枚举顺序改变结果。先算全局最优及等价集合。

`routeLowerBound` 应来自当前局部参考及地形，不能取整条剩余路线的最低点。完整臂远端低点和分腿臂端点不同，会让相同位置收到不同底线。先统一局部参考范围，再按同一范围计算高度约束。

局部高度约束需要给出实际可用空间：下方介质/地面、上方顶棚、机体及不确定性余量。窗口内没有可用高度区间时明确拒绝或重规划，不能只提高 y 后穿顶。

### B4. 终端验证必须可以执行

删除“到站位置/速度 + 到站后末尾 boost”拼接状态。到站、预测末端、终端策略起点分别保存完整快照，位置、速度、boost、库存、冷却必须属于同一时刻。

把 hold/land 从日志标签变成实际策略及阶段。主执行与预测调用同一套策略规则；所有扫描、资源推进及动作限制一致。初期优先让已有 hold 成为真正可执行策略，无法证明安全着陆时不输出 land。

不要把“预测 8 tick 后碰到下方方块，且 vy 不大”认作落地。安全着陆至少需要：

- 已验证支撑面和落点，满足机体宽度、上方净空及危险方块规则。
- 接触来自支撑面，而非侧面岸壁、树叶或顶棚。
- 接触时水平与垂直速度受限，介质明确。
- 终端动作真实进入 LAND，且实际结果再次确认。

到站后仍保留检查。若到站发生在预测时域尾部，应补足终端检查所需步数，不因只剩 1 tick 就宣称完成了完整终端检查。给总预测步数设置明确上限，记录实际检查长度。

阶段结束必须区分：路线完成、可继续保持、稳定落地、稳定入水、无法证明继续性。hold 只证明某个有限窗口可执行，不能宣称无限期可保持。

### B5. 回归与预算

必要回归：

| 场景 | 必须证明的行为 |
| --- | --- |
| ab-23 平水面反例 | 从保存状态能发现无动力平飞策略；保留水体硬拒绝 |
| 下坡转平 | 过站后不继续固定俯冲；参考、输入和评分随进度改变 |
| 弯后墙体 | 沿路线转向可以通过；切弯轨迹被扫掠拒绝 |
| 抬头遇低顶 | 拉起或点火撞顶仍被拒绝 |
| 已过站与末点 | 预测与真实过站一致；末点不提前完成 |
| 到站时仍有 boost | 终端验证从到站完整状态开始，不借用未来或过去的 boost |
| 未来点火 | 冷却、库存、活动 boost 均按模拟步更新；不能假设无限烟花或叠加 |
| 候选顺序变化 | 固定候选集合下，评分结果不依赖枚举顺序 |
| 预算不足 | 返回 budget_exhausted，不伪装成所有候选已证明不可行 |

先预热后测耗时，记录 evaluated、physicsSteps、blockQueries、cacheHits 和 native tick 耗时分布。预算不足时，优先检查已保存基线；仍无法确认安全则进入受控恢复。不要盲目把 12 ms 扩到接近整 tick。

平水面探针属于隔离回归。真实河岸安全性仍需对应世界快照或真机证据。

## 5. 批次 C：恢复要有可执行的出口

### C1. 统一几何语义，复用现有边界

修复 FlightController.surfaceBelow 将 water 跳过的问题。主飞控、终端验证与恢复应共用同一个几何查询边界，避免各自定义一次“水是什么”。

保留三种不同的问题：

| 查询 | 水的含义 | 树叶的含义 |
| --- | --- | --- |
| 当前空气飞行轨迹是否合法 | 本批水体为禁止进入的介质 | 障碍 |
| 下方支撑/表面高度 | 水面，不能读穿到河床 | 碰撞表面，不能自动作为安全落点 |
| 实测是否已入水 | 用玩家实测介质判定 | 不适用 |

按当前整格保守语义，y=62 的水格上沿按 63 处理；不要把方块坐标 62 当成机体到表面的真实净空。若未来引入流体实际形状，必须独立修改契约与测试，本批不混入。

复用 FlightSession 的机体扫掠语义，让恢复也检查宽度、顶棚、横向障碍和未知空间。向下扫描仍可用于表面参考，但不能承担前方碰撞预测。高于自身的岸壁必须通过候选的三维扫掠发现。

顺带修正 surface cache：以真正的坐标键存储，不将 `Objects.hash(x,z)` 的整数直接当唯一位置；扫描起始高度也必须进入缓存契约。同一列的顶棚下与顶棚上不是同一次表面查询。限制缓存为当前 tick/当前地图版本，防止把旧世界当新世界。

### C2. 恢复选择短期避险和着陆目标

恢复输入至少包含水平速度、垂直速度、当前姿态、活动 boost、可用烟花、可执行空间及有效控制期限。不能只按 vy、脚下高度和固定 yaw 决策。

短期动作仍可使用批次 B 的有界候选及物理扫掠，但目标改为：保持已知安全空间、降低碰撞风险、朝可达落点推进。记录首个危险接触的预测时间；单独用 vy 不能表示高速接近岸壁的风险。

点火是否值得做，由点火后的整段轨迹决定。它可能增加爬升能力，也可能让机体更快撞岸或撞顶。不要加入“距墙近就必点火”，也不要把 pitch<0 当作已经刹车。

复用主机 `flight/landing-site.ts` 的落点规则和 `movement/elytra.ts` 中已有查找流程。主机负责候选落点，客户端从实时状态验证到落点的接入和执行。落点可用不代表当前速度能飞到那里。

从 RECOVER 进入 LAND 必须带可执行着陆方案及有效地图依据。主机规划延迟期间不能先释放控制。没有可达落点时继续检查短期安全动作，并明确报告缺口；不要伪造 land 让候选过关。

### C3. 6 秒是策略期限，不是安全释放证明

分开三个时间：路线推进期限、恢复策略重算/升级期限、现有授权允许的最晚控制期限。

保留现有硬期限的权威性。本批不通过“每次进入恢复重置 6 秒”获得无限控制，也不静默延长外部授权。可以在既有控制窗口内预留恢复预算，使路线提前停止推进。

恢复的 6 秒到期时：若仍在有效控制期且未稳定结束，重新选取/执行着陆方案，或完成明确的控制移交。不得仅置 recoveryActive=false。

正常释放条件仅包括：

- 连续新鲜样本证实稳定接地，速度受限，位置与支撑面一致。
- 连续样本证实稳定入水；报告入水失败，不能转成航路成功。
- 另一个已验证控制者在同 tick 接管。

显式撤销、死亡、断开、维度变化及硬期限仍须停止当前控制。若硬期限耗尽仍在空中，报告 `control_expired_airborne` 等明确失败，而非安全收尾。保留最后状态及残余速度，不能靠漏采结束阶段掩盖它。

在有限授权、任意地形和任意故障下，无法保证永远安全落地。验收应要求本夹具的每轮在硬期限前稳定结束；如果做不到，应判恢复方案失败，先补可达落点或重定控制窗口，不能放开无限续期。

`!fallFlying` 不是落地。如果 onGround/inWater 未成立，可能仍在坠落；进入对应的失去滑翔处置或 unresolved 状态，不能直接记为 settled。

### C4. 稳定结束判据

复用 `flight/touchdown.ts` 已有的速度阈值（水平 0.5 格/tick、垂直绝对值 0.5 格/tick）作为初始分类口径。连续 20 个 native tick 满足所需条件后确认稳定结束。缺 tick、字段缺失、速度未知均不得算连续通过。

现有 helper 对缺 motion 会使用 0，不能将这个默认行为带入安全证明。修改调用前置条件或 helper 的缺失语义，并补缺速度样本回归。

“接触时速度安全”和“最终已经停住”是两个证据。撞墙掉血后站稳只能证明最终稳定，不能证明着陆安全。保留首次接触、整个 ending 的掉血和最终稳定状态。

### C5. 必须先过的反例

- 6 秒到期，仍在空中且硬期限未到：有明确 RECOVER/LAND 所有者，没有普通超时放手。
- 硬期限到期仍在空中：停止控制并输出明确失败，不报 safe_ground。
- vy 接近 0、水平高速接近岸壁：发现横向危险，不能因下沉慢而忽略。
- 低空水上：表面是水面，不是河床；既不下压入水，也不只靠增加余量穿顶。
- 拉起/点火的上方有顶棚：拒绝相应动作。
- 低 vy 横撞树叶或墙：不能判 land。
- fallFlying=false、onGround=false、inWater=false：不能判 settled。
- 已稳定落地但此前掉血并回血：物理结束成立，无损验收失败。
- 几何缓存同列不同高度、不同坐标发生 hash 碰撞：查询仍返回各自正确表面。

## 6. 批次 D：怎样复测才能归责

### D1. 先补必要证据，再跑一对

保留 ab-23 原始日志，不覆盖。新批次记录源码/客户端构建标识、路线哈希、配置、起飞状态、两臂的完整下发路径、地形版本/快照及控制参数。

每 tick 保存完整精度的决策前状态、实际输入、决策后状态或对应下一 tick，明确取样位于物理步之前还是之后。不要只留两位小数来做模型残差分析。

至少保留：native tick、session/revision、全局路线进度、phase、owner、转换原因、位置/速度、实测介质、boost 数量/剩余量/实体标识、库存/冷却、候选数量/预算、获选策略、预测轨迹摘要、拒绝分类和 HP。

交接、恢复及结束后仍使用相同 schema。字段缺失应显式为 unknown，不能填成 0 或 false。

### D2. 完整臂与分腿臂要分两种比较

“来源于同一条折线”不保证两臂是同一个控制问题。当前剩余最低高度和终端 hold 都依赖可见后缀长度。

交接等价测试应固定：同一个实测状态、同一个可见路线前缀及预测范围内的后缀、同样的终端条件、boost/库存/冷却和控制期限。只更换会话 envelope，比较目标、进度和首步动作。

若分腿端点就在预测范围内，而完整臂仍能看到后续路线，应把结果归入“路线可见范围/终端语义差异”，不能直接叫交接 bug。生产需要时再设计显式 continuation preview；本批先保证实验不混淆两种变量。

真机两臂的差异用于定位阶段，不能凭“完整失败、分腿成功”排除全部交接影响。先检查失败前状态是否已经分叉，以及最早分叉来自哪里。

### D3. 逐级放行

第一对只用于诊断。满足以下条件才做三对复现：

- 正常航路控制跨过 z=20：当 tick 正在滑翔、未入水、owner 为航路控制，速度有效且处于可继续范围。
- 每段运动通过几何检查；失败不能靠放宽水、树叶或碰撞体积消失。
- 恢复期间不自动提交普通下一腿；无双写或未声明的控制抢占。
- 内部失败后，硬期限前由明确控制者完成稳定结束，或有可核验的原子转交。
- 全程、ending 各自报告可见伤害；本夹具无损验收要求两者均为 0 且无关键缺帧。
- 记录 routeCrossing 与 recoveryCrossing，后者不能替代前者。

三对通过仅代表“早段河湾与收尾复现通过”。推进到闸门、板下和洞内后，还需逐段验证动态爬升/下降与终端可达性，不能提前宣布 E-02 通关。20 次正式批次放在这些阶段都具备完整验收条件之后。

## 7. 通过上述修复后，才调整路线余量

如果在正确反馈预测下，真实河岸状态仍无可行候选，再区分：路径几何不通、路径能通过但当前速度/姿态不可接入、所需动作不在候选集、计算/读图预算不足。

水面剖面可按以下约束设计：机体最低点必须高于水体占用上沿，并留模型误差、跟踪误差和反应距离余量；机体最高点同时低于顶棚。余量来自回放残差和实机跟踪误差，不应直接把全路线加 2 格。

爬升段应从进入该段的速度、boost 和剩余水平距离判断能否完成。需要提前爬升时，在完整高度区间内整形并重新扫掠整段。不要让 A* 单独承担烟花控制，也不要让客户端承诺任意几何折线都能飞。

职责保持清楚：规划器提供几何通道和允许的高度区间；客户端从实时状态判断、执行动态可行的动作；无法接入时返回带证据的拒绝，由主机扩大视野或重规划。当前有界 A* 可以继续保留，先修控制层再评估它的不足。

## 8. 执行边界与交付

先写能在修复前失败的回归，再改生产实现。Java 用现有 JUnit 源集；主机用所属 Vitest 项目。测试生产支持的入口，不为了注入内部字段而新增公共 API；现有离线反射探针可作诊断材料，不应成为长期接口。

只在 IO/世界查询、时间和外部输入提交处隔离依赖。不要为此拆出一串仅转发参数的服务。几何、状态转换、控制策略本身是可复用的真实边界。

每批报告实际执行的命令及结果。Java 使用现有 `:1.21.1:test`；TS 先跑受影响的 game-host 用例，再完成项目约定的 typecheck/lint。根 package.json 当前脚本名为 `typecheck`，不是 `type-check`，应使用真实存在的命令。改动扩大或局部检查发现新问题时，再扩大测试范围。

本文件只完成设计与源码核对，因此本次不产生新的 JUnit/Vitest、lint/typecheck 或真机通过结论。执行模型交付时必须分开说明：已实现、离线通过、真机通过、仍未证明。

最小合格交付不是“加两个俯仰角后飞得更远”，而是：能解释候选为何可行，预测策略可以实际执行，失败后控制权有去处，损伤和结束结果不被统计口径掩盖。
