## 1. 目标与依据

本计划采用以下产品目标作为工作定义：

> 她具有连续的人格与经历，理解用户的长期意图，在授权范围内主动工作，并通过可审阅的方式增长能力。

这是对当前方向的工程化解释。具体人格、主动程度和可委托领域仍由用户定义。

裁决原则沿用 [设计总纲](./DESIGN-PRINCIPLES.md)。Flow 的过程自由沿用
[心流自主化计划](./FLOW-AUTONOMY-PLAN.md)。社交考量与自主工作保持独立，
遵守 [社交考量计划](./CONSIDERATION-PLAN.md) 的边界。

短期先修复事件、记忆和完成判定的可靠性。长期按真实使用结果扩展能力。
本文中的新行为与验收门槛都是建议，不表示已实施或已验收。

### R1. journal 持久化与恢复

代码入口：

- `packages/stage-ui/src/stores/journal.ts`
- `packages/core-agent/src/journal/store.ts`
- `apps/stage-tamagotchi/src/main/services/airi/journal-host/index.ts`
- `apps/stage-tamagotchi/src/renderer/main.ts`
- `packages/core-agent/src/runtime/chat-orchestrator-runtime.ts`

当前写盘队列在发送前清空。失败批次没有重新入队。
当前回放仅取最后 2,000 条，并通过追加接口重新编号。
如果截断范围包含 `flow/start`，恢复代码无法重建该 Flow。

实施步骤：

1. 将两项隔离复现固化为 owning-package 回归测试。
2. 明确持久化回执、事件身份和重试去重契约。
3. 保留未获回执的批次，并按顺序重试。
4. 区分磁盘写入失败、IPC 回执丢失和成功持久化。
5. 公开待写数量、最后错误和持久化进度。
6. 保留历史事件身份，使回放序号与证据引用保持一致。
7. 复用现有 journal 投影，明确检查点与增量回放的责任。
8. 如果恢复材料不完整，公开恢复状态并暂停自动续跑。
9. 为正常关闭增加有界 flush，并定义超时后的行为。
10. 验证会话切换与重复恢复不会并发启动同一 Flow。

验收条件：

- 首次写盘失败后，两条消息最终按顺序到达持久化端。
- 写入成功但回执丢失时，重试不产生重复事件。
- 生成超过 2,000 条事件后，重启仍能定位活跃 Flow 与其证据。
- 截断、损坏尾行和序号缺口都有明确状态。
- 回放不会把旧证据引用指向另一条事件。
- 如果进程在工具结果落盘前退出，恢复后不能把该动作判定为成功。
- 正常关闭能报告 flush 结果，强制退出的保证范围有明确说明。

已有日志可能含重复编号或缺口。实施时先保存样本并识别格式，禁止静默重写历史。
任何迁移都必须保留原始日志和可审计的身份映射。

### R2. 长期记忆 SQL 写入

代码入口：`packages/memory-pgvector/src/repository.ts` 与 `src/schema.ts`。

当前唯一索引带有 `origin_id IS NOT NULL AND deleted_at IS NULL` 条件。
插入的 `ON CONFLICT (origin_id)` 没有匹配条件。
按当前建表 SQL，最小复现返回 `42P10`。

实施步骤：

1. 为实际 repository 插入路径增加数据库回归测试。
2. 使冲突目标与唯一索引采用同一契约。
3. 验证新建数据库与现有数据库的迁移结果。
4. 明确缺少 `originId` 的普通插入语义。
5. 明确删除后重投递的语义，为 R3 的删除传播提供边界。

验收条件：

- 首次插入成功，重复投递同一 `originId` 不增加第二条有效记录。
- 缺少 `originId` 时，普通插入仍可运行。
- repository 的实际生成 SQL 在隔离 Postgres 中通过。
- 迁移前后的既有事实、向量和审阅状态保持完整。

PGlite 适合快速复现 SQL 问题。真实 pgvector 验收仍使用隔离数据库。

### R3. 长期镜像状态同步

代码入口：`stage-ui` 的 memory store、本地 memory repository、Electron memory-host、
`memory-pgvector` repository。

当前 outbox 主要投递晋升时的快照。本地修订、拒绝和删除没有进入同一同步路径。
现有退避时间没有独立的到期调度，后续操作不一定会再次触发投递。

建议契约：本地事实为权威，远端保存镜像。先完成单向同步，再考虑远端召回或多端写入。

实施步骤：

1. 将待同步操作与事实变更放在同一个可靠提交边界。
2. 为插入、内容更新、审阅变更、替代、争议和删除定义传播语义。
3. 为每条事实增加可比较的版本，拒绝陈旧投递覆盖新状态。
4. 用删除标记防止旧投递复活已删除事实。
5. 将待投递状态归于单一持久化所有者。
6. 在 leader 中调度到期重试，并明确关闭与窗口切换时的清理行为。
7. 连接恢复后主动投递，受批量上限和退避限制。
8. 同步关闭时停止外部投递，并明确保留队列和远端既有副本的状态。
9. 在设置页提供队列、错误、最近成功时间和手动重试入口。

验收条件：

- 断线期间发生的更新，在恢复连接后自动到达远端。
- 重启后不丢队列，重复投递不产生重复事实。
- 批准修订后，远端旧事实同步失效。
- 拒绝和删除后，远端检索不再返回对应有效事实。
- 乱序响应不覆盖新版本，也不复活已删除事实。
- 多窗口运行时只有一个投递所有者。
- 同步关闭时没有外部投递。

这批不直接改变聊天召回来源。当前聊天召回仍以本地 DuckDB 为基线。

### R4. 完成状态与插话结算

代码入口：`core-agent` 的 `flow-completion.ts`、`chat-orchestrator-runtime.ts`，
以及 `stage-ui` 的 chat、plans 与聊天状态展示。

当前完成门异常会放行。评审模型不可用时弃权。
显式关闭的步骤可以携带 `unverified` 后结束。
这些行为包含产品政策，不能全部归为实现错误。

建议契约：执行是否结束、结果是否有证据、是否需要用户参与，分别表达。
完成门故障可以结束或暂停循环，但不能生成已验证成功。
分析任务可用观察与来源完成，不要求产生文件变更。

实施步骤：

1. 为门异常、模型弃权、无计划分析、无证据关闭分别建立回归场景。
2. 让验证状态贯穿 journal、计划卡、Flow 状态与模型收尾输入。
3. 有充分机械证据时，允许评审弃权且如实记录。
4. 如果必要证据缺失，公开未验证结果或阻塞项，并保持退出有界。
5. 先复现用户插话与 `done` 同时到达的边界，再决定修复。
6. 先处理可能改变目标的插话，再结算旧目标的完成声明。
7. 明确插话队列溢出、长文本与附件的处理结果。
8. 验证停止、切换会话与重启不会重复发布收尾或重复执行工具。

验收条件：

- 验证门故障不会显示已验证成功，也不会导致无限续跑。
- 假成功回执、失败退出码和缺少验证内容的回执不能充当所需证据。
- 纯调查任务可以零变更完成，并保留来源。
- 最后一步到达的新要求不会被队列消费后静默丢弃。
- UI 状态与模型收尾对未验证项的表述一致。

## 4. 长期可以推进的工作

### 4.1 可依赖的记忆

在可靠存储之上，测量她是否在正确时间想起正确内容。
复用现有中文评估入口，扩展改口、否定、时间变化、人物混淆与无答案样本。
分别测量召回、错误召回、修订传播与回答采纳。

事实必须带来源和适用时间。想法、自述、用户事实和工具观察保留各自身份。
对外部内容或模型自述的反复复述，不能视作新增独立证据。
压缩后的工作交接必须保留目标、约束、已验证进展与未完成项。

阶段成果：跨会话记住真实偏好，用户改口后采用新事实，不把梦境想法说成既成经历。

### 4.2 连续的人格与关系

角色卡已经提供身份基础。后续需要区分稳定人格、可变偏好、短时情绪、关系经历与当前意图。
这些状态共同影响聊天、工作叙述和主动话题，但不改变授权与证据规则。

优先复用角色卡、memory 与 journal 的现有边界。
`core-character` 空入口本身不构成创建大型人格引擎的理由。
长期偏好变化要有来源、审阅和回退路径，避免单次模型输出改写身份。

阶段成果：跨任务、跨天和重启后仍能保持可辨认的性格，并解释与用户共同经历的事情。
这一部分需要用户对自然感和关系连续性的长期评价。

2026-09-06 承接记录：PC-0 至 PC-2 已补齐最小作用域契约和有界连续性投影。
记忆使用 `userId + characterId` 隔离；无作用域旧记录不进入行为 prompt；真实 provider、
跨角色重启、共同经历场景和长期关系评价仍未完成。实现与检查记录见
[人格连续性执行计划](./persona-continuity-plan.md#5-完成定义与执行记录)。

### 4.3 持续的目标管理

已有长周期计划结构，需要补齐调度责任。
长期 goal 要能等待外部条件、定时复查、响应新事件、处理过期信息和恢复中断。
已验证完成、暂时等待、需要用户、取消与失败必须区分。

先选择一种重复发生的真实工作做完整闭环。
例如：跟踪一个项目的待办，或整理一类待处理信息。
通过后再扩展领域。目标调度复用 Flow 执行，社交心跳保持独立。

阶段成果：用户不用反复催促，同一个授权目标可跨天推进，并在必要时带着具体问题求助。

### 4.4 注意力与资源分配

聊天、Flow、外部事件、旁路问答和梦境整理需要共享可解释的优先级与资源约束。
明确谁可以打断谁、哪些工作可以等待、什么情况下需要停止模型调用。
成本统计覆盖主模型、摘要、抽取、评审和后台决定。

主动话题以真实事件和用户可接受的时机为依据。
分别测量重复话题、无效打断、漏报重要事件和等待用户的时间。

阶段成果：她知道何时开口、何时继续工作、何时等待，并能解释自己的当前状态。

### 4.5 可审阅的能力增长

已有 skill-forge、提交入口、审阅与哈希绑定基础。
下一步验证完整循环：发现重复工作、提出技能、自测、人工审阅、使用、测量收益与退役。
先选一个低风险且重复发生的任务，避免批量生成没有使用场景的技能。

记录成功率、维护成本与重复失败。修改源码后使旧审阅失效。
外部执行器返回的报告保留来源等级，不能自动变成可信变更证据。

阶段成果：至少一个自造技能在后续任务中反复产生收益，并可在退化时停用和恢复。

### 4.6 长期运行与维护

建立固定任务集与连续使用记录，按任务类型分别报告结果。
测量任务成功率、虚假完成、用户纠正次数、恢复成功率、记忆错误、成本和打扰感。
模型、prompt、工具和压缩策略的变化在同一任务集上比较。

对 journal 全量克隆、跨窗口快照、向量计算和长时间窗口驻留采集性能数据。
有证据后按所有权、持久化或生命周期拆分模块，避免按行数机械重构。
补齐数据导出、恢复、配置诊断与可识别构建，降低日常维护成本。

阶段成果：连续使用期间的问题可追踪、可复现，升级收益可测量。

## 5. 距离目标的判断

| 阶段 | 完成含义 | 当前判断 |
|---|---|---|
| A：能力贯通 | 人格、聊天、工具、Flow、记忆、主动表达都有代码路径 | 主要骨架已形成，组合验收仍有缺口 |
| B：可靠日用 | 中断和故障不破坏状态，完成表述可信，记忆可纠正 | 尚未毕业，R1–R6 优先推动这一阶段 |
| C：持续自主 | 同一目标跨天推进，注意力、权限、等待和成本有明确责任 | 有部分基础，需要独立设计与真实任务验证 |
| D：长期陪伴与成长 | 人格和关系连续，主动行为合适，经验能改善后续表现 | 属于长期产品实验，现有机制尚不足以证明 |

当前更接近“能力贯通的原型，正在走向可靠日用”。
距离可日常使用的第一版，主要剩下有限的工程修复与验收。
距离能长期托付、具有连续关系体验的版本，还需要目标调度、行为质量和持续评估三个闭环。

功能存在比例不能代表目标完成比例。一次演示、一次成功任务或一组单元测试也不能代表长期表现。
阶段 B 的工期可在故障回归和迁移范围确定后估计。
阶段 C、D 需要跨天乃至跨周的使用记录，无法仅按代码量给出可信截止日期。

建议的下一次里程碑是：完成短期修复，选择固定任务集，再进行 7 天日用试验。
7 天是建议的观察窗口，不是当前稳定性结论。
通过后再进行 30 天跨会话试验，记录用户纠正、记忆修订、目标推进与主动行为。
这些观察窗口用于发现问题，不能证明无限期可靠性。
