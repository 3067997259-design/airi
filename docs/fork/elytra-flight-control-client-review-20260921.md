## 3. 客户端的三个优先问题

### 3.1 等待动作可以把低空滑翔机带进水层

`FlightSession.beginHold` 把目标设为沿当前速度方向前方 48 格、低 16 格，并禁止等待期间点火。16 号进入 holding 时，对应目标高度约 49.291，所在河段水面高度为 63。

此后实际保持 pitch=-60，水平速度降低，下降逐渐增大，进入水层。这里不能只用“俯仰向上”判断是否在安全爬升。

保持动作虽然也经过短时扫掠，但它脱离了主机验证的路线，且扫掠把水当成可通行。因此“仍有输入所有者”不能等价于“仍在安全通道里”。

下一步要求：只有经过验证的剩余路线或逃逸路线才能承接等待。按当前速度、下降率、净空和实测规划延迟，提前决定是否还能等待。低空不能统一采用向下 16 格的等待目标。

源码：`D:/mcpfabric/src/client/java/dev/mcpfabric/client/flight/FlightSession.java` 的 `beginHold`、`advanceEntries`、`tick`。

### 3.2 无碰撞空间和空中飞行介质被合并了

`FlightController.flightBlockQuery` 将空碰撞形状（包含水）转成 `passable`。`FlightSession` 接受该标记；`FlightDynamics` 却只有空中滑翔模型，没有水中状态。实测入水后 `gliding` 仍为 true，因而只检查这个标志不能发现模型失效。

用原始 Java `FlightDynamics` 对 16 号实测状态做一步重放：

| 初始 tick | 模型下一步速度 vx/vy/vz | 实测下一 tick 速度 |
| --- | --- | --- |
| 785176，入水前 | 0.047887 / -0.234943 / -0.325477 | 0.047889 / -0.234944 / -0.325477 |
| 785180，入水后 | 0.029563 / -0.282196 / -0.309949 | 0.036168 / -0.231159 / -0.245803 |
| 785205，已停滞 | -0.001354 / -0.040549 / -0.003866 | 0 / -0.025779 / 0 |

下一步要求：把碰撞、危险和介质分别表达。水面上方可以飞，进入水体不能继续假设空中动力学。加入原生 inWater/介质状态和一步预测误差；检测到介质切换时，明确退出飞行跟随并进入对应恢复/收尾状态。

不需要为了这次修复实现完整水中规划器，但必须停止让空气模型“预测”水中飞行。

### 3.3 起飞后的可用烟花没有形成完整供应流程

`BotController.equipRocketOffhand` 只从背包搬一发到副手。起飞消耗它后，`FlightController.driveSession` 只向决策器提供 `countRocketsInHands`，并且没有补弹步骤。背包库存多不代表驱动可以点火。

16 号库存 623→622，所有 flight-session 样本均没有点火。这与上述缺口一致。但证据没有保存当时双手物品，所以不能仅凭该记录把所有停滞都归因于缺弹。

下一步要求：分别记录库存、手中可用数量、装备请求/确认和真实点火/boost 确认。客户端飞行所有者必须负责补充可用烟花。用“副手仅一发、背包还有余量”的场景验证起飞后的再次推进。

补弹也不是入水后的充分修复：离线探针在 785225 的实测状态和快照上，将可用烟花参数从 0 改为 64，原始决策器仍选择不点火。探针将计算预算放宽到 1000ms 以隔离预算，候选上限和评分不变。查询将快照空气和水映射为 passable，其余格按障碍；它不能代替完整原生碰撞形状，也不是实机恢复成功的证据。

源码：`D:/mcpfabric/src/client/java/dev/mcpfabric/client/BotController.java:771`、`D:/mcpfabric/src/client/java/dev/mcpfabric/client/flight/FlightController.java:355`。

## 4. 交接还缺少实际状态能接入路线的保证

客户端允许在新入口 2×entryReach（当前 16 格）范围内采纳新腿；旧腿完成时还会绕过这项距离门槛。采纳没有先验证从实测位置、速度、高度和介质到新腿的连接轨迹。

16 号在水中零水平速度、距入口 13.442 格时仍采纳了第 3 腿。它符合现有代码条件，但不能称为可执行交接。

主机也在 pending 被采纳前就用新腿覆盖 `activePath`。因此前缀核查和下一次预规划可能已经围绕未来路线工作。需要将执行中的路线和待接入路线分开持有；只有原生采纳回执才能推进执行状态。

同理，偏离路线超过 24 格后跳过前缀校验只消除了错误比较，没有完成“起飞状态接入低空通道”。16 号 yMax=124.418，而首条路线最高 74.5。必须有明确的起飞后接入阶段，不能将偏离本身当成继续执行的证明。

源码：`FlightController.adoptPendingIfReady`；[elytra.ts](../../apps/stage-tamagotchi/src/main/services/airi/game-host/movement/elytra.ts) 的早交接分支与前缀核查分支。

## 5. A* 保留的职责与剩余问题

A* 能提供几何连通路线。它当前没有表达进入各段时的速度、可用推进、可持续高度、转弯能力和介质。这些条件在低空平飞和交接时已经需要，不应等到羊毛闸门才处理。

先保留现有几何规划器及身体扫掠。客户端已有短时预测，可以在此基础上增加通道约束、预测末端的可继续飞行条件和真实状态反馈。没有证据支持此时整体换掉 A* 或引入另一套完整搜索系统。

规划器还有两个应记录、但不应抢占当前主线的问题：

- 直连候选的 cost 只包含距离和爬升，没有肩环墙代价；搜索候选使用 `spaceRouteCost` 包含墙代价。因此仍未完全“同币比较”。
- 只要存在开天候选，带顶候选就不参加比较；“开天”又只表示已读窗口内没发现顶。闸门/板下/洞口之前，需要恢复对合法带顶通道的共同评估，避免再次被引向障碍上方。

## 6. 下一批：冻结路线选择，先验证飞行执行能力

1. **修正并复现上述失败链。** 覆盖一发副手烟花后的再次推进、低空结束一腿但下一腿延迟到达、入水后 gliding 仍为 true、入口附近却无法接入新腿。先重放 16 号，再做短真机实验。
2. **使用同一条经过扫掠的河湾诊断路线比较。** 从相同位置、速度、姿态、推进状态和库存出发，分别完整下发与分腿下发；路线坐标完全一致。另行验证桥面起飞后接入该路线。固定路线只用于隔离故障，不写成生产夹具特判。
3. **根据结果决定后续工作。** 完整下发也失败，继续修驱动/模型/推进；完整通过而分腿失败，修交接/等待；两者都通过而在线生成路线失败，才返回前沿选择或路径形状问题。

河湾验收必须以实际跨过约定截面为准，记录位置、速度、介质、输入所有者与路线修订。失败收尾分别报告安全接地、稳定入水、仍在空中、未知；稳定入水可以是明确的失败终态，不能计作 E-02 抵达成功，也不能只改 `airborneAtReturn` 布尔值便宣布收尾完成。

河湾通过之后，依次验证闸门、板下和洞内平台。每个狭窄段都要同时验证进入状态、通过轨迹及出口后续能力，最后再跑每场景 20 次正式批次。
